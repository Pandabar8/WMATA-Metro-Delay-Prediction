2. Layer 1 · Configuration

Everything the pipeline needs is centralized in scripts/config.py: API key, endpoint URLs, polling intervals, the database path, and the delay threshold.

The pattern (all three look like this)

def collect_once():
    trains = fetch_predictions()       # GET request with api_key header
    count  = store_predictions(trains) # tag with UTC timestamp, INSERT
    return count
Key trick: every row gets a collected_at timestamp in UTC. This is what lets you reconstruct what the API said at any moment in the past — the foundation for computing observed headways later.

5. Layer 4 · Orchestration

There are two ways the pipeline can run, and the project uses both at different times.

Continuous loop · run_pipeline.py

One process that sleeps 1 second at a time and fires each collector when its interval has elapsed. Used for local testing.

while running:
  if elapsed >= 120s: collect_predictions()
  if elapsed >= 300s: collect_incidents()
  time.sleep(1)

Catches SIGINT/SIGTERM for clean shutdown. Prints stats every 10 min.

Per-cycle script · collect_all.py

One short-lived process per cycle. Cron fires it every 2 min on the Oracle Cloud VM. This is what actually ran for 5 weeks straight.

# crontab on VM
*/2 * * * * cd /path && python collect_all.py

Simpler operationally: if it crashes, cron just fires it again two minutes later. No long-running process to babysit.

The trade-off: the continuous loop is more efficient (one DB connection, fewer process startups). Cron is more robust (no babysitting, no memory leaks, automatic restart on failure). For a 5-week unattended run on a free-tier VM, robustness wins.

6. Layer 5 · Sync (VM → local)

Why merge instead of overwrite: if you ever ran the local pipeline (e.g., during testing), or if a VM sync fetched a partial snapshot, overwriting would lose data. Merging by row content is safe.

8. Layer 7 · The headway-based delay label

This is the most consequential 50 lines in the entire codebase. The WMATA API returns time-to-arrival, not delay, so the project had to invent its own definition.

The four-step recipe

Step 1 · Detect arrivals

A train has "arrived" when its minutes field becomes "ARR" or "BRD" (boarding). Mark every such row.

df["is_arrival"] = df["minutes"].isin(["ARR", "BRD"])

Step 2 · Compute observed headway

For each (station, line, direction), look at consecutive arrivals and measure the gap.

arrivals["prev_arrival"] = arrivals.groupby(
    ["location_code", "line", "group_num"]
)["collected_at"].shift(1)

arrivals["observed_headway_sec"] = (
    arrivals["collected_at"] - arrivals["prev_arrival"]
).dt.total_seconds()

Step 3 · Compute the median headway per hour

The median is grouped by (station, line, direction, hour). Each window is compared against itself, not a global average.

group_keys = ["location_code", "line", "group_num", "_hour"]

group_medians = (
    arrivals
    .dropna(subset=["observed_headway_sec"])
    .groupby(group_keys)["observed_headway_sec"]
    .median()
)
Why hourly: trains run every 4 min at rush hour but every 12 min at midnight. A 10-minute gap is normal at 1 AM and a delay at 8 AM. A global median would label every off-peak gap as a "delay" — exactly the bug that pushed the early delay rate up to 37%.

Step 4 · Apply two filters

A train is labeled delayed = 1 only when both conditions hold:

threshold_sec = 2 * 60  # DELAY_THRESHOLD_MINUTES from config

is_phantom = observed_headway > 2 * median_headway

is_delayed = (
    (observed_headway > median_headway + threshold_sec)
    & ~is_phantom
)
  • Threshold filter: the gap must exceed the median by at least 2 minutes.
  • Phantom filter: if the gap is more than 2× the median, it's almost certainly a missed arrival between polls (a train arrived and left in the 2-minute polling blind spot), not a real delay.

Step 5 · Propagate labels back to all prediction rows

Arrivals are sparse (a few per station per hour). Predictions are dense (one every 2 min). merge_asof attaches each arrival's delay label forward in time to the prediction rows that led up to it.

df = pd.merge_asof(
    df,
    delay_map,
    left_on="collected_at",
    right_on="arrival_at",
    by=["location_code", "line", "group_num"],
    direction="forward",       ← look forward to the next arrival
    tolerance=pd.Timedelta("15min"),
)
The result: every prediction row now carries the label of "what eventually happened next at this station / line / direction." That is the supervised target the model learns to predict.
